## Расхождения, которые нужно исправить

### 1. P1 — на главной остался несуществующий маршрут подтверждения email

[LandingPage.tsx:58](/home/arseny/RiderProjects/CoffeePeek.FE.WebClient/coffee-peek/src/pages/LandingPage.tsx:58) при открытии `/?token=…` выполняет `POST /api/user/confirm-email?token=…`. Ни контроллера, ни gateway-маршрута для него нет. Сервер принимает `PUT /api/Users/me/email-confirmation?token=…`: [UsersController.cs:361](/home/arseny/RiderProjects/CoffeePeek-NET/CoffeePeek.AccountService/Controllers/UsersController.cs:361).

В приложении уже есть корректный `confirmEmail()` и отдельная страница подтверждения. Использовать их и убрать второй прямой `fetch`/параллельный сценарий на главной.

### 2. P1 — редактирование отзывов расходится по ID и телу запроса

Форма читает `GET /api/CoffeeShopReviews/{publishedReviewId}`, затем передаёт тот же ID в `PUT /api/ModerationReviews/{id}`. Например, [ReviewsPage.tsx:199](/home/arseny/RiderProjects/CoffeePeek.FE.WebClient/coffee-peek/src/pages/ReviewsPage.tsx:199) передаёт `item.id`. Однако [UpdateCoffeeShopReviewHandler.cs:28](/home/arseny/RiderProjects/CoffeePeek-NET/CoffeePeek.Moderation.Application/Features/Review/UpdateCoffeeShopReview/UpdateCoffeeShopReviewHandler.cs:28) ищет запись в **ModerationReviewRepository**. Опубликованный Review и ModerationReview имеют разные ID; связь хранится в `moderationReviewId`.

Второе расхождение: [updateReview():894](/home/arseny/RiderProjects/CoffeePeek.FE.WebClient/coffee-peek/src/api/coffeeshop.ts:894) без преобразования отправляет `ratingCoffee`, `ratingPlace`, `ratingService`. [UpdateCoffeeShopReviewCommand.cs:13](/home/arseny/RiderProjects/CoffeePeek-NET/CoffeePeek.Moderation.Application/Features/Review/UpdateCoffeeShopReview/UpdateCoffeeShopReviewCommand.cs:13) требует `rating: { coffee, place, service }`. Существующий POST создания принимает плоские оценки, а PUT обновления — нет. Поэтому одинаковый тип для create/update неверен.

Кроме того, форма редактирования загружает/удаляет фото и отправляет `photos`, но update-command не содержит поля фото и handler их не обновляет. `visitedAt`, который форма отправляет при создании и редактировании, отсутствует и в `PublicCreateReviewRequest`, и в update-command; этот выбор даты сервер не использует.

Нужны отдельные DTO создания/редактирования и явно выбранный ID для PUT. Сохранить published ID для чтения/жалоб и moderation ID для текущего update API; либо добавить API обновления по published ID с разрешением связи на сервере. Возможность редактировать фото/дату должна быть согласована с серверным контрактом.

Локально исполнена реальная функция `updateReview()` с подменённым транспортом: она отправляет published ID, плоские оценки, `photos` и `visitedAt` ровно в описанном виде. HTTP-ответ сервера этим воспроизведением не проверялся.

### 3. P1 — админка запрашивает пользователей по UUID через публичный slug API

[users.ts:19](/home/arseny/RiderProjects/CoffeePeek.FE.WebClient/coffee-peek-admin/src/api/users.ts:19) вызывает `GET /api/users/{userId}`. В `ShopEditPage`, `ShopChangeRequestsPage` и `ShopChangeRequestDetailPage` сюда приходят UUID из административных DTO: `userId`/`submittedByUserId`.

Теперь этот путь обслуживает [PublicUserAddressesController.cs:28](/home/arseny/RiderProjects/CoffeePeek-NET/CoffeePeek.AccountService/Controllers/PublicUserAddressesController.cs:28) и разрешает **slug**. UUID запрещён правилами [PublicSlug.cs:21](/home/arseny/RiderProjects/CoffeePeek-NET/CoffeePeek.Shared.Domain/PublicAddresses/PublicSlug.cs:21). `/internal/users/{id}` существует для межсервисных обращений и не предназначен для браузера.

Предпочтительно возвращать имя/необходимую сводку автора в административном DTO заявки или добавить защищённое административное чтение по UUID. Для страницы списка это также уберёт дополнительные запросы по каждому автору и кофейне из `useQueries`.

### 4. P1 — редактирование обжарщика в админке использует UUID в публичном API

Административный каталог возвращает UUID; переход на `/catalogs/roasters/:id` сохраняет его. [RoasterEditPage.tsx:53](/home/arseny/RiderProjects/CoffeePeek.FE.WebClient/coffee-peek-admin/src/pages/RoasterEditPage.tsx:53) вызывает [roasters.ts:158](/home/arseny/RiderProjects/CoffeePeek.FE.WebClient/coffee-peek-admin/src/api/roasters.ts:158), то есть `GET /api/roasters/{UUID}`. [RoastersController.cs:18](/home/arseny/RiderProjects/CoffeePeek-NET/CoffeePeek.ShopsService/Controllers/RoastersController.cs:18) принимает slug.

Добавить административное получение полного редактируемого DTO по UUID — `GET /api/admin/roasters/{id}`. Сейчас в admin-controller есть list/create/update/delete, но нет detail. Публичный DTO также не отдаёт `cityId`, который нужен форме; отдельное административное чтение решит обе проблемы.

### 5. P1 — просмотр каталога/карты в админке читает старые публичные DTO

[coffeeShops.ts:139](/home/arseny/RiderProjects/CoffeePeek.FE.WebClient/coffee-peek-admin/src/api/coffeeShops.ts:139) ожидает `id` и строковый `address`. Текущие `PublicShopSummaryDto`/`PublicMapShopDto` содержат `address: { slug, canonicalPath, … }`; адрес улицы находится в `location.address`. В admin-interceptor нет адаптера этих DTO.

Локально исполнены действующие API-функции на объектах, соответствующих [PublicDiscoveryDtos.cs:28](/home/arseny/RiderProjects/CoffeePeek-NET/CoffeePeek.Contract/Dtos/PublicAddresses/PublicDiscoveryDtos.cs:28):

| Вход | Фактический результат админки |
|---|---|
| Список кофеен с `address.slug` и `location.address` | `id: ""`, текст адреса `"[object Object]"` |
| Карта с `address.slug` | Маркер без `id` |

Это ломает ключи строк/маркеров и переход к деталям. Добавить адаптер публичных DTO: `id = address.slug`, навигация по `canonicalPath`, адрес улицы из `location.address`. Имена `getBrowseCoffeeShopById` и `BY_ID` для публичных сущностей заменить на `BySlug`, чтобы не смешивать их с UUID административных сущностей.

### 6. P1 — загрузка аватара не повторяет подписанный заголовок

[ProfilePage.tsx:125](/home/arseny/RiderProjects/CoffeePeek.FE.WebClient/coffee-peek/src/pages/ProfilePage.tsx:125) отправляет presigned PUT только с `Content-Type`. Полученный из `POST /api/Photos/avatar` URL формирует общий [MinIOStorageService.cs:44](/home/arseny/RiderProjects/CoffeePeek-NET/CoffeePeek.MediaService/Services/MinIOStorageService.cs:44), который подписывает также `x-amz-tagging: is_permanent=False`.

Пропуск подписанного заголовка приводит к несовпадению подписи при загрузке. Остальные загрузчики клиента и админки этот заголовок передают. Использовать уже существующий `putPhotoToStorage()` и для аватара; затем проверить реальную загрузку в MinIO. HTTP storage в рамках аудита не вызывался.

### 7. P2 — поля доступности создания отзыва объявлены, но не заполняются

`CanCreateReview` и `ExistingReviewId` есть в private/public DTO кофейни. В текущих Shops Application/Persistence нет вычисления/присваивания этих полей: [GetCoffeeShopHandler.cs:43](/home/arseny/RiderProjects/CoffeePeek-NET/CoffeePeek.Shops.Application/Features/CoffeeShop/GetCoffeeShop/GetCoffeeShopHandler.cs:43) персонализирует только посещение, чекины и helpful-статус.

[useMyReview.ts:8](/home/arseny/RiderProjects/CoffeePeek.FE.WebClient/coffee-peek/src/hooks/useMyReview.ts:8) выбирает режим редактирования лишь при `canCreateReview === false`; с `null` он не узнаёт о существующем отзыве. Восстановить расчёт персональных полей и явно описать, какой ID возвращается для редактирования.

### 8. P2 — типы ответа и сообщения о результате создания отзыва не соответствуют API

`createReview()` обещает `ApiResponse<Review>`, а POST возвращает `CreateEntityResponse`. `updateReview()` также обещает Review, но PUT возвращает `{ reviewId }`. Сейчас форма в основном проверяет успех, поэтому ошибка типов скрыта.

Форма сообщает «Отзыв успешно опубликован», хотя POST `/api/ModerationReviews` создаёт заявку на модерацию. Исправить типы результата и сообщение на отправку/обновление заявки. GET опубликованного отзыва и GET отзывов пользователя требуют авторизации на сервере; `getReviewById()` с `requiresAuth: false` следует привести к этому контракту. Сейчас token всё равно прикрепляется interceptor, поэтому само значение флага не доказывает отказ запроса.

## Что упростить и улучшить

1. **Разделить публичные slug и административные UUID в TypeScript.** Использовать разные DTO и типы `PublicSlug`/`EntityId`, ясные `BySlug`/`ById`, отдельные адаптеры DTO. Не заменять все ID на slug глобально: review/check-in/photo/moderation ID остаются служебными.
2. **Один источник контрактов.** Экспортировать OpenAPI из реальных сервисов, генерировать типы/клиент и проверять frontend↔backend в CI. Генерация должна описывать фактические ответы; например, `ShopChangeRequests/{id}` возвращает разные публичный/admin DTO в зависимости от роли, а сейчас аннотация описывает только административный.
3. **Проверять интеграционные сценарии, которые сейчас отсутствуют в тестах.** Подтверждение email с главной, чтение автора и обжарщика по UUID в admin, просмотр list/map с текущим Public DTO, изменение опубликованного отзыва с nested rating и правильным moderation ID. Существующие mock-тесты не проверяют эти связки.
4. **Унифицировать response/pagination на границе клиента.** Сейчас встречаются `items`, `coffeeShops`, `reviewDtos`, `totalItems`/`totalCount`, `page`/`currentPage`, envelope и raw DTO. Централизованный адаптер и точные типы позволят убрать многочисленные `any`, варианты PascalCase/camelCase и fallback-поиск полей. Новый серверный формат вводить с совместимостью/версионированием.
5. **Сократить дублирующие HTTP/auth реализации.** Две почти одинаковые системы refresh/requestInterceptor имеют уже разное поведение. Общий небольшой transport/auth пакет может убрать расхождения, сохранив DTO и права каждого приложения. `_token` в create/update review не используется; токен берётся interceptor — параметр можно убрать.
6. **Объединить чтения одной сущности и query keys.** Сейчас есть `publicAddress` и `coffeeShops/detail`, `/by-slug/{slug}` и короткий путь с тем же чтением. Общий query-options builder позволит не делать повторные detail-запросы в формах и аккуратно обновлять кэш. Сроки кэширования публичных адресов/видимости менять только с сохранением текущих требований актуальности.
7. **Сократить N+1 в административных списках заявок.** Добавить минимальные сведения автора/кофейни в admin list DTO или batch lookup вместо нескольких detail-запросов на строку. Не смешивать этот admin API с анонимным публичным профилем.
8. **Каталог напитков использует одну таблицу, но два разных представления.** `/api/menu/drinks` отдаёт `data.drinks` без Other, `/api/catalogs/drinks` — массив с Other и nullable category. Оба используются.
